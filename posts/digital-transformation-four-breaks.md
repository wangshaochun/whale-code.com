## 先说结论

我们的体感是：验收会上最好看的那套东西，往往就是之后最没人用的那套。

花几百万上 ERP，上千万建数据平台，再拉一块大屏做经营看板。验收那天功能齐全、页面漂亮、材料齐整。半年后回头看，员工还在导出 Excel 统计，部门之间还在微信群传文件，老板要一份经营分析，还得临时找人取数。

系统就这么变成了两件事：领导来了打开，验收时汇报。

王自如和帆软 CEO 陈炎、FDE 专家沈涛聊过这个话题。他们说的那些问题，跟我们做项目时踩过的坑基本对得上：毛病多半不在技术和软件，而在业务、数据、组织这三件事从开头就没搭上。下面四个断点，是我们见得最多的。

## 一、把买系统当成了做数字化

一提数字化，第一反应是列采购清单：财务上 ERP，生产上 MES，办公上 OA，分析上 BI。系统一年比一年多，预算一年比一年大。

然后你会发现：上了 ERP，各科室照样导 Excel 二次加工；上了经营分析平台，月度数据还是财务手工拼；上了生产管理系统，计划员排产还是在自己的 Excel 里调。

这不全是员工不配合。多数时候，系统里根本走不通他手上那件事。

王自如举的例子是排产。一张 Excel 计划表搬进系统，看着是“线上化了”，可排产背后是设备状态、订单优先级、物料到货时间、换型成本，还有老师傅的经验。这些规则没梳理清楚，软件换几套都一样，无非是把原来的操作方式搬进浏览器。

所以立项之前，三个问题绕不过去：

- 现在最疼的业务问题是哪一个，疼在哪个环节、谁在疼？
- 系统上线后，哪几个动作会变，谁的动作要变？
- 三个月后，拿什么判断它有用？

第三个问题最容易被跳过。答不上来，验收标准就只剩“功能清单打勾”。

## 二、审批搬上线了，业务还在线下

第二个断点更隐蔽：系统不少，链路是断的。

销售用 CRM，采购用 ERP，生产用 MES，仓库用 WMS。每个部门都有自己的系统，部门之间还是靠人传。

一张客户订单进来，正常要经过库存核查、生产排期、采购备料、生产执行、发货结算。听起来是一条线，实际是：销售把订单信息发到群里，计划员复制进 Excel，采购重新核对一遍物料，仓管再问一次货什么时候到。

王自如在访谈里说得很直接：“只要我的审批流在线上了，我就已经完成了业务的数字化，其实并不完全是这样。”

批在线上走完，活儿在线下干。系统记下了“谁同意了”，没记下“事情是怎么发生的”。

*图 2：上半截是流程图，下半截是实际动作。*

这里还有个容易漏掉的点：过程。排产因为设备停机、客户插单改过三次，如果系统只留最后下发那一版，前面两次为什么改、改完影响了什么，就全没了。他特别强调过，每一次变更的上一个版本都是过程数据，应该被保留、被追溯。

对制造企业来说，这些“改来改去”的记录，后面做交期预测、算插单损失，都是原料。

## 三、数据收上来了，口径没统一

第三个断点，钱花得最多，效果最不明显。

数仓建了，中台建了，BI 也上了，报表几百张。可真要跨部门看一个数，还是对不上。

常见场景：季度利润下滑，管理层问原因。财务说成本涨了，销售说产品结构变了，生产说效率掉了，采购说原料涨价。四套数、四个说法，看着都有道理，会开两小时，结论是没有结论。

不是数据没采，是没治。同一个指标各部门口径不同，同一个客户在不同系统里编号不同，系统之间的数据对不上号。

王自如讲过他推指标管理的做法：组织各部门写指标管理白皮书，把定义统一下来。他对指标字典的定位挺有意思：“这个字典的价值是什么呢？不是大家每天做业务的时候翻这个字典，而是当大家吵架的时候，靠这个字典来解决。”

这话说到根子上了。统一口径表面是统一字段和算法，实际是统一各部门对同一件事的理解。

落到动作上，一般是四件事：

- 数据集成：ERP、MES、CRM、WMS 之间的数据真正接通，不再靠导出文件
- 指标治理：收入、成本、利润、库存这些核心指标只有一个定义
- 数据建模：客户、订单、产品、物料之间能关联起来
- 数据质量：数据准确、完整、连续，出了问题能追到源头

### 数据怎么被用起来

治理完还有一层：业务人员怎么拿到数据。

过去主要靠固定报表和 BI 看板。管理层看经营报表，业务看指标看板，临时有个问题，找数据员取数、做表、发邮件，一来一回两天。

AI 进来之后，这块在变。沈涛提到，数据消费不必止于报表和看板，还可以是 HTML 报告、千人千面的呈现，甚至直接自然语言问数。

帆软的产品按这个思路铺。面向大型企业的本地化 Data Agent 平台 Dora，前面用 FineDataLink 做集成，后面靠 FineBI 的指标中心和语义层托底，指标中心正在升级到 2.0。面向中小微企业的云产品走“以用促治”，直连电商平台标准 API，接入账号就能出经营分析和归因。标准化场景下，一两天能看到初步结果。用沈涛的话说，这是围绕新的数据消费方式，把过去积累的治理和再生产能力放大。

不过企业级 Agent 和个人用的 Agent 不是一回事。个人 Agent 出错，用户自己兜着；企业 Agent 后面连着公司数据库，要管权限、管安全、管结果准不准。王自如那句话我记得很清楚：“企业的数据 Agent 如果 mess up 整个公司的数据库，这是个巨大的事故。”

## 四、上线即终点，之后没人负责

最后一个断点，不少公司到现在还没意识到：建设责任很清楚，使用责任没人认领。

立项时，IT 管选型，业务提需求，供应商交付，领导批预算，链条清清楚楚。

上线之后呢？谁持续优化？谁推动业务部门真用起来？谁查数据质量？出了问题找谁？这几个问题，多数项目没有答案。

沈涛讲过一个制造业客户的例子。那家企业做经营分析，难的其实不是把数据整出来，而是分析会开完之后：谁跟踪问题、谁推动整改、整改怎么考核。

所以除了建设机制，还得有一套运营机制：

- 每套系统有明确的业务负责人和管理责任人
- 数据质量和指标维护有固定的人、固定的频率
- 定期收业务部门的使用反馈，别等到年底调研
- 系统使用和经营分析、业务改善绑在一起
- 发现的问题有人、有措施、有时限

## 几点补充

原文的分析就到这儿，我们补三条自己的看法。

**验收即终点，是机制问题，不是认识问题。** 项目制预算奖励交付，不奖励使用：钱按节点拨、按验收付、按上线剪彩，没人因为“第三年还有多少人在用”拿奖金。所以光喊“要建运营机制”没用。真要改，得让付款节奏跟使用效果挂钩，把使用率和数据质量写进业务部门的考核，再给数字化团队一个常设编制。项目制不动，下一个项目还是同一个结局。

**指标之争，本质是考核之争。** 口径为什么统一不了？因为口径背后是排名和奖金。指标白皮书如果没有一把手或财务负责人签发、不进考核，它就只是一份文档。数据治理动的是权限和利益的分配，这也是它推不动、只能靠外部顾问顶着的真正原因。

**“以用促治”对中小企业是对的，但有天花板。** 从一个高频场景切进去，快速见效，解决的是没人愿意为治理付费的冷启动。可一旦要跨业务线合并口径、做集团报表，前面省下的治理债会连本带利还回来。稳一点的做法是：以用促治起步，同时把指标定义和主数据编码一开始就做对。这两件事前期便宜，返工极贵。

最后说句最不技术的。经营分析会本身就是失效的：汇报、点评、散会，没人跟进。这样的会，配再好的 BI 和大屏，也只是把无效会议开得更快更漂亮。先跑通“问题—责任人—措施—时限—复盘”这个循环，用 Excel 都行，跑顺了再上系统，才不至于又买一套摆设。

## FAQ

**Q：预算有限，先做治理还是先上 BI？**  
A：先挑一个能算清账的场景，把它的指标口径定死，再做看板。反过来做，看板越漂亮，争议越大。

**Q：数据中台一定要建吗？**  
A：不一定。接口不多、口径清楚的企业，数仓加一层指标层就够了。中台的价值在跨系统复用，没到那个量级，它就是负担。

**Q：上了 AI 问数，是不是就不用治理了？**  
A：正好相反。自然语言问数会把口径问题放大，因为提问的人不会替你解释“这个利润含不含税”。
