## 先说结论

CDP 能不能用，不看标签数量，看三件事：

1. **OneID 有没有打通**：同一个人在不同系统里是不是同一个人
2. **口径有没有统一**：同一个“活跃用户”，运营、财务、技术是不是同一个定义
3. **标签有没有被用起来**：能不能圈人、能不能 API 输出、能不能解释

很多项目做完变成“标签仓库”：标签几百个，业务还是靠 Excel 取数。问题不在技术，而在设计顺序反了。

正确顺序是：**先定业务问题和口径 → 再做 OneID 和数据模型 → 再做标签 → 最后做服务化**。

## 一、先定业务目标

CDP 常见的三类目标：

| 目标 | 典型场景 | 成功标准 |
|---|---|---|
| 营销转化 | 人群圈选、分层触达、活动复盘 | 转化率、复购率、触达成本 |
| 运营分析 | 用户画像、漏斗、留存 | 取数效率、口径一致性 |
| 客户服务 | 360 视图、权益、风险 | 响应速度、信息完整度 |

目标不同，标签体系差别很大。不要一上来就建“全量标签”，先做 2–3 个能闭环的场景。

## 二、OneID：CDP 的地基

### 1. 常见 ID

- 手机号、邮箱
- 微信 OpenID / UnionID
- 会员 ID、客户号
- 设备 ID、Cookie
- 企业统一社会信用代码（B2B）

### 2. ID 映射

建立 `id_mapping` 表，记录不同来源 ID 的关联关系和置信度：

```text
one_id | id_type | id_value | source | confidence | updated_at
```

规则示例：

- 手机号相同 → 高置信度合并
- 微信 UnionID 相同 → 高置信度合并
- 设备 ID + 登录行为 → 中置信度
- 仅浏览行为 → 低置信度，不强行合并

### 3. 不要追求 100% 打通

匿名流量、多设备、家庭共用账号，永远有噪声。目标是把“可识别的核心客户”打通，并保留置信度和合并来源，方便回溯。

## 三、数据模型

至少分四层：

| 层 | 作用 | 示例 |
|---|---|---|
| ODS | 原始数据 | 订单、会员、行为日志 |
| DWD | 明细宽表 | 用户、订单、商品、门店 |
| DWS | 主题汇总 | 用户日/月汇总、品类偏好 |
| ADS | 标签/应用 | 标签宽表、人群包、API |

标签不要直接在 ODS 上算，否则口径和性能都会失控。

## 四、标签分层

### 1. 事实标签

直接从数据里取，不加工或轻加工：

- 性别、年龄、城市
- 注册时间、首单时间、最近登录时间
- 会员等级、所属门店

### 2. 统计标签

按时间窗口聚合：

- 近 30 天订单数、近 90 天消费金额
- 近 7 天活跃天数
- 客单价、退货率
- 品类偏好 Top3

### 3. 规则标签

由业务规则计算：

- 高价值客户：近 12 个月消费 ≥ 5000 且订单数 ≥ 3
- 流失预警：近 90 天未登录且历史有订单
- 新客：首单在 30 天内
- 风险客户：退款率 ≥ 30% 且客单价低于均值

规则要可配置、可追溯，不要硬编码在 SQL 里。

### 4. 模型标签

用模型预测：

- 购买倾向
- 流失概率
- 生命周期阶段
- 推荐品类

模型标签要有版本、训练时间、特征列表和效果指标。没有评估的模型标签不要上线。

## 五、标签定义模板

每个标签必须有一份“说明书”，否则半年后没人知道它怎么来的：

```yaml
name: 近30天高活跃用户
code: active_30d_high
entity: user
type: statistic
definition: 近30天内登录天数 >= 10 且有效行为次数 >= 50
source: dwd_user_behavior
window: 30d
update: daily 02:00
owner: 数据运营-张三
sensitivity: L2
lifecycle: 长期
```

最少包含：名称、编码、实体、类型、口径、数据源、更新频率、负责人、敏感级别、生命周期。

## 六、计算架构

### 1. 批处理

- Hive / Spark / Doris / ClickHouse
- 适合日级/小时级标签
- 注意分区、幂等、重跑

### 2. 实时

- Kafka + Flink
- 适合实时行为、实时人群
- 实时标签不要太多，优先核心场景

### 3. 存储与服务

- 标签配置：MySQL
- 标签结果：ClickHouse / Doris / HBase
- 检索：Elasticsearch
- 人群圈选：ClickHouse / Doris + 位图（Bitmap）
- API：统一标签服务，不要把数据库直连给业务

## 七、标签服务

至少提供四类能力：

1. **查询**：按用户查标签
2. **圈选**：按标签组合圈人群，返回人数和人群包 ID
3. **输出**：人群包推送到短信、企微、广告平台
4. **解释**：这个标签为什么命中的，数据来自哪里

API 示例：

```http
POST /api/tags/query
{
  "one_id": "U-10001",
  "tags": ["active_30d_high", "high_value", "churn_risk"]
}
```

圈选接口要限制组合复杂度，避免一次查几十个标签把库拖垮。

## 八、治理：决定能活多久

- **指标字典**：名称、口径、负责人、更新频率
- **血缘**：标签来自哪张表、哪个字段、哪个规则
- **质量**：空值率、枚举分布、波动监控
- **成本**：每个标签的存储和计算成本，定期下线无用标签
- **权限**：按部门/角色控制标签可见性，敏感标签单独审批
- **生命周期**：临时标签设过期时间，避免无限膨胀

## 九、常见失败原因

1. **OneID 没打通**：同一个人三个 ID，标签各算各的。
2. **口径不统一**：运营的“活跃”和技术“活跃”不是一个定义。
3. **标签只建不用**：没有圈选、没有 API、没有业务闭环。
4. **全量重算**：每天全量跑几亿行，成本高还慢。
5. **没有负责人**：标签错了没人认，最后全部下架。
6. **敏感数据裸奔**：手机号、身份证直接进标签表。
7. **一开始追求大而全**：做了 500 个标签，业务只用 10 个。

## 十、验收清单

- [ ] OneID 覆盖率和置信度可解释
- [ ] 核心指标口径有唯一文档
- [ ] 标签分层清晰，命名规范
- [ ] 每个标签有负责人、更新频率、敏感级别
- [ ] 批处理/实时链路有幂等和重跑机制
- [ ] 圈选性能满足业务要求
- [ ] 标签 API 有鉴权和限流
- [ ] 敏感字段脱敏，权限可审计
- [ ] 标签血缘可查
- [ ] 至少 2 个业务场景闭环并有数据复盘

## FAQ

**Q：CDP 和数据中台是什么关系？**  
A：CDP 更偏客户数据和营销应用，数据中台是更宽的数据能力底座。CDP 可以建在数据中台之上，也可以独立先做。

**Q：标签越多越好吗？**  
A：不是。标签要有使用场景、负责人和维护成本。没有使用的标签就是负债。

**Q：OneID 一定要做到 100% 吗？**  
A：不可能。重点是核心客户可识别、合并规则可解释、置信度可追溯。

**Q：实时标签有必要吗？**  
A：只有实时营销、实时风控等场景需要。大多数运营标签日级/小时级足够。
